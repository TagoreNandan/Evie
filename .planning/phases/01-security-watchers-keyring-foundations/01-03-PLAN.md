# Plan 01-03: HIBP Breach Monitor & 2FA Audit Integration

## Objective

Build `integrations/breach_watch.py` for scheduled email breach monitoring via Have I Been Pwned (HIBP) API v3, and `integrations/twofa_audit.py` for checking 2FA enrollment status on GitHub accounts while documenting Google 2FA API constraints.

## Tasks

### Task 1: Implement HIBP Breach Watcher (`integrations/breach_watch.py`)
- **Type**: tracer
- **Description**: Build `BreachWatcher` class with `check_email_breaches(email: str, key_name: str = "hibp_api_key") -> list[dict]`.
  - *Credential Management*: Retrieve the HIBP API key via `keyring_utils.get_credential("evie_assistant", key_name)` rather than requiring callers to pass plaintext credentials.
  - *HTTP Specifications*: Query HTTPS URL `https://haveibeenpwned.com/api/v3/breachedaccount/{urllib.parse.quote(email)}?truncateResponse=false`. Include required headers: `hibp-api-key: <key>` and descriptive `User-Agent: Evie-Security-Assistant`.
  - *Explicit Design Decision*: Direct email lookup via HIBP v3 API sends the URL-encoded email address to HIBP over HTTPS. K-anonymity is not selected for Phase 1 and is explicitly deferred.
  - *HTTP Error Contract*: HTTP 404 is explicitly defined as "no breach found" (returns `[]`). HTTP 401 (unauthorized), 403 (forbidden), 429 (rate-limited), and 5xx (server error) MUST raise or return explicit error statuses — NEVER convert API failures into "0 breaches".
  - *Privacy & Output Security*: Never log, print, or persist the HIBP API key. Do not output full email addresses in stdout or log files (redact email local part). Returned findings contain only minimal breach metadata (`Name`, `Domain`, `BreachDate`, `DataClasses`).
  - *Testing*: Unit tests in `tests/test_breach_watch.py` must mock `keyring_utils` and `httpx` HTTP requests, verifying credentials and PII are not exposed in logs or exception messages.
- **Files**:
  - `integrations/breach_watch.py`
  - `tests/test_breach_watch.py`
- **Threat Model**:
  - *Risk*: API key or email PII leaked in logs/errors, or API failures masked as zero breaches.
  - *Mitigation*: Mask log outputs, enforce HTTPS, validate HTTP status codes, and load credentials strictly via OS Keyring.
- **Automated Verification**: `pytest tests/test_breach_watch.py`

### Task 2: Implement Account 2FA Auditor (`integrations/twofa_audit.py`)
- **Type**: task
- **Description**: Build `TwoFactorAuditor` class with `audit_github_2fa(token_key: str = "github_token") -> dict` and `audit_google_2fa() -> dict`.
  - *GitHub 2FA*: Retrieve GitHub token via `keyring_utils.get_credential("evie_assistant", token_key)`. Query authenticated user endpoint `GET /user` and inspect documented private field `two_factor_authentication` (boolean). Document explicit scope requirement (`read:user` or `user` OAuth scope required to access this field).
  - *Google 2FA*: Standard Google OAuth userinfo API does NOT expose 2FA status for personal accounts, and no supported non-admin Google API exists for inspecting personal 2FA. Mark Google 2FA auditing as deferred/blocked pending identification of a documented, supported API mechanism (SEC-04 requirement preserved, limitation made explicit without inventing unsupported approximations or inferring status from unrelated account metadata).
  - *Testing*: Unit tests in `tests/test_twofa_audit.py` must mock keyring and API responses.
- **Files**:
  - `integrations/twofa_audit.py`
  - `tests/test_twofa_audit.py`
- **Threat Model**:
  - *Risk*: Plaintext token management by callers or false security claims from unsupported API guesses.
  - *Mitigation*: Retrieve GitHub tokens via OS Keyring and document API limitations explicitly for Google 2FA without fabricating mock status.
- **Automated Verification**: `pytest tests/test_twofa_audit.py`

## Verification Strategy

- Run unit test suite: `pytest tests/test_breach_watch.py tests/test_twofa_audit.py`
