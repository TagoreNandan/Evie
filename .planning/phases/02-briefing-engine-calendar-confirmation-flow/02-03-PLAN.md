# Plan 02-03: Confirmation-Gated Calendar Actions (`integrations/calendar_actions.py`)

## Goal
Implement two-step confirmation-gated calendar scheduling (`CAL-01`, `CAL-02`). Any proposed calendar creation, update, or deletion must produce a proposal token and require explicit user confirmation before executing any Google Calendar API mutation.

## User Review Required
> [!IMPORTANT]
> - `POST /calendar/propose` MUST NEVER call the Google Calendar API directly. It only creates a proposal record in `calendar_actions` SQLite table (`confirmed_by_user = 0`, `status = 'proposed'`) and returns a confirmation prompt with a unique `proposal_token`.
> - `POST /calendar/confirm` only executes Google Calendar API mutations when `confirmed` is explicitly `True`, `proposal_token` has not expired (TTL 15 min), and an atomic SQLite claim succeeds (`status = 'claimed'`).
> - OAuth tokens must NEVER appear in API responses, log files, exceptions, database records, or test outputs.

## Proposed Changes

### Component 1: Integration Handler

#### [NEW] [`integrations/calendar_actions.py`](file:///Users/somespecies/Desktop/Evie/integrations/calendar_actions.py)
- Create module docstring referencing section 6 of `02_TRD.md` and `CAL-01`/`CAL-02`.
- Constant: `PROPOSAL_TTL_SECONDS = 900` (15 minutes expiration).
- Implement `init_calendar_actions_table(db_path: str)` to create `calendar_actions` SQLite table per `04_Backend_Schema.md` (with columns `id`, `proposal_token`, `action_type`, `event_summary`, `start_time`, `end_time`, `description`, `event_id`, `confirmed_by_user`, `status`, `executed_at`, `created_at`).

- Implement `propose_calendar_action(db_path: str, action_type: str, summary: str, start_time: str, end_time: str, description: str = "", event_id: str | None = None) -> dict`:
  - **Input Validation**:
    - Validate `action_type` in `['create', 'update', 'delete']`.
    - Validate ISO-8601 timestamps (`start_time`, `end_time`) using standard `datetime.fromisoformat()`.
    - Require `end_time > start_time` for `create` and `update`.
    - Enforce max string lengths: `summary` <= 255 chars, `description` <= 2000 chars.
    - Require non-empty `event_id` when `action_type` is `'update'` or `'delete'`.
  - **Proposal Token Generation & Persistence**:
    - Generate unique `proposal_token` (UUID4 string).
    - Insert proposal row into `calendar_actions` with `confirmed_by_user = 0`, `status = 'proposed'`, and current ISO timestamp.
  - Return formatted prompt response: `proposal_token`, `status = 'proposed'`, `prompt` ("Are you sure you want to {action_type} event '{summary}'? Reply confirm to proceed."), and `proposal_details`.
  - **ZERO external HTTP / API calls performed.**

- Implement `confirm_calendar_action(db_path: str, proposal_token: str, confirmed: bool) -> dict`:
  - **TTL / Expiration & Cancellation Check**:
    - Query `calendar_actions` for `proposal_token`. If not found, raise `ValueError("Invalid proposal token")`.
    - Check age (`now - created_at`). If > 15 minutes, update proposal `status = 'expired'` and return `{"status": "expired", "message": "Proposal expired. Please request a new proposal."}` with zero external API calls.
    - If `confirmed` is `False`: update proposal `status = 'cancelled'` and return `{"status": "cancelled", "message": "Calendar proposal was cancelled."}` with zero external API calls.
  - **Atomic Confirmation Claim**:
    - Execute atomic SQLite claim query:
      `UPDATE calendar_actions SET status = 'claimed', confirmed_by_user = 1 WHERE proposal_token = ? AND status = 'proposed' AND created_at >= ?`
    - If affected rowcount == 0 (already claimed, executed, or cancelled), raise `ValueError("Proposal token already claimed or processed")`.
  - **Explicit Lifecycle & Google Calendar API Execution**:
    - Update proposal `status = 'executing'`.
    - Retrieve Google OAuth access token via `keyring_utils.get_credential("evie_assistant", "google_calendar_oauth")`. If missing, set `status = 'execution_failed'`, raise `RuntimeError("Google Calendar credentials not found in OS keyring")`.
    - **Credential Secrecy**: Ensure OAuth token is strictly passed in `Authorization: Bearer <token>` header without logging or exposing token value in exceptions/tracebacks.
    - Execute Google Calendar REST API v3 operation using `httpx.Client`:
      - `create`: POST `https://www.googleapis.com/calendar/v3/calendars/primary/events`
      - `update`: PUT `https://www.googleapis.com/calendar/v3/calendars/primary/events/{event_id}`
      - `delete`: DELETE `https://www.googleapis.com/calendar/v3/calendars/primary/events/{event_id}`
    - Handle API response:
      - If HTTP success: record `event_id` (from created resource if new), set `executed_at = CURRENT_TIMESTAMP`, `status = 'executed'`. Return `{"status": "executed", "event_id": event_id, "summary": summary}`.
      - If HTTP failure: update `status = 'execution_failed'` (do **not** mark as executed), raise safe HTTP error response without token leakage.
